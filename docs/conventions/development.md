# Development

Conventions for the dev shell, pre-commit hooks, Nix and config file style, CI, and failing checks.

## Dev Shell

The Nix flake provides Nushell, `sqlite3`, `ripgrep`, `zstd`, and `git-cliff`, together with the pre-commit tooling:

```bash
nix develop              # Dev shell with the tools and the hooks
nix flake check          # Hooks, the Home Manager module tests, and every Nushell test
nix build                # Build the command, its wrapper, and the installed skill
```

## Pre-Commit Hooks

Entering the dev shell in this repository installs a [pre-commit](https://pre-commit.com) hook generated by [`git-hooks.nix`](https://github.com/cachix/git-hooks.nix). The shell generates its config, `.pre-commit-config.yaml`, as a gitignored symlink in each checkout, which is why [`AGENTS.md`](../../AGENTS.md#rules-for-every-change) asks for `nix develop -c true` in every new worktree.

The hook runs file hygiene, Nix formatting and lints, EditorConfig, Prettier for JSON and YAML, Markdown lint, `cspell`, `actionlint`, and `nu-check` on the staged files. Hooks that fix files in place fail the commit if they make changes, so stage the fixes and commit again.

Fixtures under `stores/fixtures/` are byte-for-byte inputs, so the hook excludes them.

`nu-check` fails only on diagnostics with severity `Error`, because `nu --ide-check` exits 0 even when it finds one. A deprecation warning passes, so rerun the tests on a Nushell upgrade and read the warnings there.

## Nix Style

`nixfmt` formats `flake.nix` and the files in `nix/`, and `statix` and `deadnix` lint them. These rules cover what the tools leave open:

- Keep code within 100 columns, counting the indent, and wrap comments by hand, since `nixfmt` does not reflow them.

- Mark the file header with `=` banners at column 0, and mark each section with `-` banners indented to match the code around them. Every banner line ends at column 100. A file without banners stays without them:

  ```nix
  # ==================================================================================================
  # agent-project-move Home Manager Module
  # ==================================================================================================

          # ------------------------------------------------------------------------------------------
          # Module Options
          # ------------------------------------------------------------------------------------------
  ```

- Put each argument of a top-level function on its own line, even when the list would fit on one. Take `...` only when the caller passes a broader set, as with flake outputs. A `callPackage` derivation omits it, so an unexpected argument fails.

- Declare each dependency of a `callPackage` file as its own argument, as nixpkgs does, so `.override` can replace it. Put `lib` first and the other arguments in alphabetical order. In the flake, reach packages through `pkgs`.

- Put `inherit` entries first in a `let` block and in a call's argument set. In a set that returns data, keep each `inherit` where its entry belongs.

- Group related bindings and attributes, and order a `let` block so that each binding follows what it depends on. Within a group, use alphabetical order unless a stronger order applies.

- Follow a multiline binding or attribute with a blank line before its next sibling. Keep single-line siblings together and separate their groups with a blank line.

- Take `nushell` from `nixpkgs-unstable`, because nixos-26.05 ships 0.112.2 and the modules need `str lowercase` from 0.114.

- Write multiline text, such as a shell hook, as an indented string with literal line breaks.

## Config Style

Prettier, Taplo, and the JSON formatter leave long strings alone, and no formatter covers shell code, so wrap YAML, TOML, and shell files by hand:

- Keep other lines within about 100 columns, counting the indent. Leave a line long when it holds an unbreakable token, such as a URL or path, or sits in a heredoc body or literal block whose line breaks are content.
- Split a shell command that runs past the limit at its pipelines and `&&` or `||` lists. Indent continuation lines one level past the first line, and end each line but the last with `\`, unless it ends with `|`, `&&`, or `||`, which already continue the command. In a workflow, write the command in a `run: |` block.
- For a multiline command substitution, put the command on the next line and the closing `)` on its own line, aligned with the assignment.

## CI

CI runs on pushes to `main`, pull requests, and manual dispatch, and the release workflow calls it again for each tag before publishing. The `nix` job runs `nix flake check` and `nix build` on Linux and macOS, and the `result` job reads every job of the run attempt from the Actions API and fails when any job other than itself concluded anything except success or skipped.

Branch protection requires only `CI Result`. It catches a matrix leg cancelled before a runner picks it up, which the `needs` results omit, so a new job joins its `needs`. A skipped job counts as passing, which is why the gate runs after a failure too.

The Nix jobs pull from the `hakula` Cachix cache, and runs on `main` or by the maintainer push their builds to it. The cache only saves build time, so a failed Cachix setup logs a warning and the job builds without it.

Each job sets `timeout-minutes` to several times its usual duration, so a hung job stops at that limit, where it would otherwise hold the runner for GitHub's six-hour default. Give each new job a limit the same way.

## Failing Checks

Fix the cause of a failing hook, test, or CI job. Skipped tests, `--skip` or `--exclude` flags, ignore and allowlist entries, `continue-on-error`, `|| true`, retries, and special cases for one path or commit only hide the failure.

Keep an ignore or allowlist entry only when it is the design, such as a fixture whose bytes are the input, and give the reason in the PR that adds it.
